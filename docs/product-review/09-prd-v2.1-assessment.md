## 一、总体结论（给决策用的三句话）

1. **方向批准**：该 PRD 是我们 P2-1「AI 行动执行框架」中"需审批"档的正确细化。「AI 评估、人决定」「不可行 ≠ 沉默拒绝」「敏感度决定审核深度」三原则与我们"可审计 AI"战略完全同向，其中**三个设计点是市场上的真差异化**（详见第五节）。
2. **规格退回修订**：按可实施规格标准存在 **8 条 blocker**——核心审批机制自相矛盾（quorum 会签 vs "顺序决定"DB 红线）、数据模型装不下自己定义的会签、全文规范性依赖仓库中不存在的 V1/V2 条款。需出 V2.1a 勘误稿后才能排期（修订清单见第六节）。
3. **排期按"从零新建"口径**：PRD 自称"增补模块"，但代码库中不存在任何 Action Engine V1/V2 实现（全仓 grep 零命中）。真实工作量 = 政策规则库 + 评估器 + 审批链引擎三个子系统从零建，且其三条核心承诺分别硬依赖我们尚未修复的 B-00（无出站投递）、B-21（无通知）、B-15（无用户管理）。建议分三期插入既有 Roadmap（见第七节），**不要强插 30/60 天窗口**。

## 三、代码库落地评估（现实检验）

**C-1 前置依赖链（硬性，不可绕）**

| PRD 承诺 | 撞上的现状 | 必须先做 |
|---|---|---|
| "客户进度更新 100% 覆盖、杜绝黑洞" | **B-00：无出站投递**——客户连"已提交审核"都收不到 | P0-1 出站投递（Roadmap D30） |
| SLA 50% 提醒 / 超时升级候补 / Slack·Telegram 告警 | **B-21：无通知系统**，且产品无 Slack 集成 | P0-4 通知（D30）+ IM 告警立项 |
| 值班审核员/组长/Supervisor/Finance/Legal 审批角色 + roster | **B-15：无用户管理**，Role 枚举只有 4 值 | P0-5 用户管理（D60）；审批职位建独立维度表，不污染工单 Role |
| 评估器以 intent 为输入（Step 1 之后） | 现引擎无意图识别（L1 是关键词 includes） | P1-5 意图打标（D90）提为前置 |

**C-2 数据层**：需新建 6 张表 + 4 个枚举（全部带 tenant_id 沿用现有隔离索引模式）；`conversation_id` 在现有模型无对应实体，应删除或映射 ticket_id；`customer_id` 外键指向 end_users。规则库可复用现有 `SyncStatus` 枚举实现"非 synced 不参与评估"（与知识库同源治理，PRD 该条款与现有架构天然契合 ✅）。规则版本化用 immutable 版本行（改规则 = 插新版本），cited_rules 存 `{rule_id, version}`。

**C-3 状态机**：送审期间工单在现有 6 状态中**无合法落点**（留在 ai 会被 loop guard 和后续消息继续触发 EVA；借用 handoff 语义错误）。方案：新增 `review` 状态 + 三事件（ai→review 送审、review→ai 批准接回、review→handoff 拒绝转人工答复），同步更新转移表、ingest 的开放态判断（避免重复建单）、入站守卫（review 态客户消息作为"补充资料"写入链而非触发 EVA）。

**C-4 §7-3 DB 约束的可实现性**：Postgres 纯 CHECK 无法跨行校验，需三层组合——BEFORE UPDATE trigger（approved 时断言 ≥3 个不同决定人且 decided_at 单调递增）+ 可声明式硬化部分（职责分离直接用 `UNIQUE(chain_id, decided_by_user_id)` 唯一索引；`CHECK(decision='reject' → reason IS NOT NULL)`）+ 服务层事务内 `SELECT FOR UPDATE` 复核。trigger 走手工 SQL 迁移（Prisma 不原生管理）。

**C-5 审计**：现有唯一审计表 ticket_events 以 ticketId 为必填外键，规则变更/roster/链模板/级别边界这些**非工单实体的变更无处落账**。需新增租户级 `audit_logs(entity_type, entity_id, action, before, after)` 通用审计表；审批决定双写（audit_logs + 关联工单的 ticket_events）。

## 五、战略评估（CEO 视角）

**与 P2-1 的关系**：是其"需审批"档的深度细化，非冲突。但有一处设计分歧必须解决：评估器对**全流量**生效且无只读豁免——评估器超时/低置信时查询类请求也会被送人工队列（S0 层 4 小时），破坏我们 D180 验收①"查询类零人工解决率 ≥40%"的达成空间。**修订：评估器仅闸"写操作/有副作用"意图，查询/只读意图绕过或走 machine_hint 确定性快速通道**；A 类放行显式引用 P2-1 的"自动执行"档。

**市场水位**："人工审批门 + 审计"本身已是行业收敛能力（Fin Tasks、Agentforce Command Center、Decagon AOP、Gorgias Actions），不构成卖点。该 PRD 的**真差异化是三点**：① 版本化政策规则库 + 100% 规则引用红线（竞品无对应物）；② "先例一致"维度 + 先例自动沉淀（竞品无对应物）；③ 按规则条目聚合的推翻率 → 自动产出规则修订建议的校准闭环。对外叙事应把这三点与我们"零割裂人机同台"打包为**「可审计 AI 决策」**；多级链作为企业治理配置项低调交付，不作宣传主轴。

**运营现实（必须调参）**：S3 默认"每层 30–45 分钟 + 24/7 计时 + ≥3 个不同 user_id"对我们种子客户（5–15 人游戏客服团队）意味着约 6 个 on-call 名额的全年无休排班；可用审核人不足 3 人的租户，其 S3 需求在数据层**永远无法批准**。修订：S3 默认随租户工作日历（24/7 改为可选）；每层默认 SLA 放宽至 2–4 小时；首发 KPI 目标 S3 ≥90–95%（而非 99%）；DB 红线改为"≥N 个不同 user_id，N 租户可配（默认 3、最小 2），N=2 时强制冷静期 + 二次确认"作小租户补偿控制。原则 2 的本质是"不黑洞 + 诚实承诺 + 进度推送"，不是 90 分钟极速终审。

**PRD 没想到但必须补的三件事**：
1. **上线前仿真**：评估器是会拦客户请求的组件，不经历史回放验证等于拿真实客户试误拦率。把 P3-2 的最小版（历史工单批量回放 → A–E 判定分布 + 预计送审量报告）提为一期门槛，替代对不存在的 V2-B6 的引用；影子模式运行 2–4 周达标后才开闸。
2. **审批的移动/IM 触达**：30–45 分钟 SLA 撞上"审核人不在工位"——分派即推送（浏览器+邮件+IM），S0/S1 支持 IM 内联审批（同意/拒绝+理由回填 Audit）；原型只有 1100px 桌面断点，移动审核视图需与审核台基础版同期。
3. **事故模式**：线上事故可在一小时产生数百条同类 C 类需求，每单一链 + S2+ 禁批量会淹没队列。增加"同类聚合审一次、结果批量应用（每单仍留独立 Audit 行）"的事故通道，与 P2-4 异常聚类共用检测管线。

**成本设计**：machine_hint 可机判部分（期限天数/金额上限/状态白名单）应做**确定性预检**——零 LLM 成本、无 3 秒超时风险，只把机判不了的模糊地带交 LLM 五维评估。既对齐 Decagon 的确定性执行理念，又延续我们成本路由审计的差异化。
