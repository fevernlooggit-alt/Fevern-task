§1 · 总体结论

方向批准 · 规格退回 · 排期重估

✓ 方向批准

「AI 评估、人决定」「不可行 ≠ 沉默拒绝」「敏感度决定审核深度」三原则与我们「可审计 AI」战略完全同向，是 P2-1 行动执行框架中「需审批」档的正确细化。三个设计点是市场上的真差异化。

⟲ 规格退回修订

存在 8 条 blocker：核心审批机制自相矛盾（会签 vs 顺序 DB 红线）、数据模型装不下自己定义的会签、全文规范性依赖仓库中不存在的 V1/V2 条款。需出 V2.1a 勘误稿后才能排期。

↺ 按「从零新建」重估

PRD 自称「增补模块」，但代码库不存在任何 Action Engine 实现（全仓检索零命中）。真实工作量 = 规则库 + 评估器 + 审批链三个子系统从零建，且核心承诺硬依赖尚未修复的 B-00 / B-21 / B-15。

§2 · PRD 规格问题（条款引用均经核验属实）

三条 Blocker 与九条 Major

编号级别问题修订建议
P-1Blocker会签与 DB 红线矛盾：§3.2 允许 S3 并行会签（2/3 同意），§7 红线却要求 DB 强制「≥3 个不同 user_id 的顺序决定」；会签层算几个决定、反对票是否计入均无定义红线改为按赞成票计数并给出规则，或 S3 禁用会签

P-3Blocker幽灵依赖：V2-A1/A2/B6、V1 Step 1-9 等被引用条款在仓库与全部材料中零命中；评估器插入点、风险信号底座、回放引擎、学习闭环均悬空增加「依赖现状」章节逐条标注真实状态；估算改全量新建口径

P-7Major送审期间工单状态、客户撤回、审核期新消息路由整段缺失；链状态无 cancelled新增工单 review 状态与撤回/新消息规则
P-8Major评估器故障时残缺信号大概率算低分落 S0——最高不确定性场景反而进最松审核链故障时 E 类默认按 S2 保守档装链，写入红线断言
P-9Major评估器在身份验证之前运行，冒用者可污染风险信号与先例库；「审批通过后验证失败」的链终态未定义身份验证前移或「未验证」计入风险分；补链 void 终态

P-11Major「话术不含终局性拒绝词」红线无词表/模板作判定标准，且话术只有中文（客户是 zh/en/ms 三语）受控模板三语落库；断言改「白名单模板 ID 渲染」+ 禁用词表
P-12Major「AI 不可行被推翻率 <15%」未定义 E 类是否计入分母，计入会虚增推翻率误触规则修订推翻率只算 C+D；E 类单列为置信度校准指标

四条硬前置 + 五项工程决策

PRD 承诺撞上的现状必须先做
「客户进度更新 100%，杜绝黑洞」B-00 无出站投递——「已提交审核」这句话客户都收不到P0-1 出站投递（D30）

评估器以 intent 为输入现引擎无意图识别（L1 为关键词匹配）P1-5 意图打标（D90）
  • 数据层：新建 6 张表 + 4 个枚举；conversation_id 在现有模型无对应实体应映射为 ticket_id；规则库「非 synced 不参与评估」可直接复用现有 SyncStatus 治理（与知识库同源，天然契合 ✓）；规则版本化用 immutable 版本行。
  • 状态机：送审期间工单在现有 6 状态中无合法落点（留在 ai 会被 loop guard 继续触发 EVA）。需新增 review 状态与三事件：送审、批准接回、拒绝转人工答复。
  • §7-3 DB 约束：Postgres 纯 CHECK 无法跨行校验，需 trigger + 唯一索引（职责分离用 UNIQUE(chain_id, decided_by_user_id) 硬约束）+ 事务内服务层复核三层组合。
  • 审计：现有审计表以工单为必填外键，规则/值班表/链模板变更无处落账——需新增租户级通用 audit_logs 表，审批决定双写。
§4 · 原型实测（真实浏览器驱动，6 组场景）

抓到一个会误导开发的 Bug

PT-1  升级敏感度产生同人两层。 对 REQ-0030（S2，当前层 Finance·Pei Shan）点「升级敏感度 S2→S3」后，审批链变为 Supervisor → Finance·Pei Shan → Finance·Pei Shan——同一人占据两层，直接违反 PRD 自己的职责分离条款（§3.2-6）。升级逻辑追加固定模板层，不检查已在链上的审批人。
编号发现
PT-2「要求补充」仅弹提示、链状态不流转；PRD 要求的第 5 个动作「转人工直接接管会话」整体缺失（实测动作条只有 4 项）
PT-3S3 最终层「二次确认」实为同一弹窗内的红字警示，非独立第二次确认——交互定义需 PRD 澄清
PT-4承诺时间自相矛盾：客户话术「预计 2.5 小时」但链 SLA 之和为 2 小时（呼应 P-10）
PT-5队列仅按 SLA 剩余排序（PRD 要求 SLA↑+Risk↓ 复合）；筛选 chips 无功能；会签未建模；值班配置页为占位
PT-6工程提示：详情页 SLA 倒计时不刷新；innerHTML 直接拼接客户文本（XSS 面）——原型不能作为实现直接复制

实测确认做对的（正式实现应保留）：空理由提交拦截 ✓ · S0/S1 免理由、S2+ 强制理由（与 PRD 一致）✓ · 拒绝话术自动附申诉引导、链终止后不可再操作 ✓ · 理由框可多选带入引用规则 ✓ · 角色视角切换后权限正确收敛 ✓。整体信息架构与 PRD §4 高度一致，作为设计沟通稿质量合格。

§5 · 战略评估

三个真差异化 + 三处必须调参

值得放大的三点（竞品矩阵中均无对应物）：① 版本化政策规则库 + 100% 规则引用红线；② 「先例一致」维度 + 先例自动沉淀；③ 按规则条目聚合的推翻率 → 自动产出规则修订建议的校准闭环。与我们「零割裂人机同台」打包为「可审计 AI 决策」对外叙事；多级审批链本身已是行业收敛能力（Fin Tasks、Agentforce Command Center、Decagon AOP），作为企业治理配置项低调交付。
  • 设计分歧必须解决：评估器对全流量生效且无只读豁免——超时/低置信时查询类请求也被送人工队列，破坏 D180 验收「查询类零人工解决率 ≥40%」。修订：只闸「写操作/有副作用」意图，查询类走 machine_hint 确定性快速通道（零 LLM 成本、无超时风险）。
  • 运营现实：S3 默认「每层 30–45 分钟 + 24/7 + 3 个不同审批人」对 5–15 人客服团队 ≈ 6 个 on-call 名额全年排班；审批人不足 3 人的租户 S3 永远批不出来。修订：默认随工作日历、每层 2–4 小时、KPI 首发 90–95%、审批人数 N 租户可配（最小 2 + 强制冷静期）。
  • PRD 没想到的三件事：上线前历史工单回放仿真（评估器会拦客户请求，不回放验证等于拿真实客户试误拦率）；审批的移动/IM 触达（分派即推送 + S0/S1 IM 内联审批）；事故模式（同类需求突增时聚合审一次、结果批量应用，每单仍留独立审计行）。
§6 · 给 PRD 作者的修订清单（V2.1a 必改项）

十二条修订要求

  1. R-1解决会签 vs 顺序 DB 红线矛盾（P-1），补投票子表（P-2）
  2. R-2增加「依赖现状」章节，V1/V2 引用逐条标注真实状态；估算改全量新建口径（P-3）
  3. R-3分级边界左闭右开 + 多档取最高（P-4）；补 Risk Rate 完整计分表并统一法务口径（P-5）
  4. R-4补 B 类循环上限/超时/退回恢复规则（P-6）；补送审期工单状态、撤回、新消息路由（P-7）
  5. R-5评估器故障默认落 S2 保守档并写入红线（P-8）；身份验证前移或计入风险分，补审批后验证失败终态（P-9）
  6. R-6SLA 承诺口径统一：单一默认值 + 缓冲系数 + 日历折算 + 重算规则（P-10、PT-4）
  7. R-7话术改受控模板 zh/en/ms 三语落库；红线改模板 ID 断言 + 禁用词表（P-11）
  8. R-8KPI 口径：推翻率剔除 E 类（P-12）
  9. R-9评估器只闸写操作意图；A 类放行显式对接 P2-1「自动执行」档
  10. R-10S3 默认参数下调（工作日历 / 2–4h / 90–95% / N 可配最小 2）
  11. R-11新增：回放仿真门槛、分派即推送 + IM 内联审批、事故聚合模式、先例冷启动策略、多意图拆分
  12. R-12原型修正：升级跳过已在链上的审批人（PT-1）、补「转人工接管」与退回流转（PT-2）、明确二次确认交互（PT-3）、复合排序与筛选实装（PT-5）
