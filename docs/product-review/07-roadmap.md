# 交付物 7 — 实施 Roadmap（30 / 60 / 90 天 + 6 个月）

> 团队假设：2 前端 + 2 后端 + 1 AI 工程 + 1 QA + 1 产品（可伸缩，负责人栏按此写）。
> 原则：先闭环（客户收得到回复），再运营（客服用得下去），再竞争力（SLA/自动化），再差异化（行动执行/QA/飞轮）。

---

## 第 1 阶段 · 30 天快速整改（"能真实运营"）

**目标**：修复一票否决项与 S1 缺陷，达成端到端闭环：客户提问 → AI/人工回复 → 客户收到 → CSAT 雏形。

| 项 | 内容 | 负责人 |
|---|---|---|
| 功能 | P0-1 出站投递（Telegram + LiveChat widget 收信）；P0-2 收件箱可运营化；P0-4 浏览器通知；P0-7 URL 路由 | 后端 A / 前端 A |
| 修复 | B-01 cron 排序污染、B-03 分页、B-09 滑块、B-10 输入法、B-11 删除确认、B-14 假模型项、B-17 README | 全员分摊 |
| 前端 | react-router 改造；无限滚动；投递状态角标；通知权限引导 | 前端 A/B |
| 后端 | OutboundAdapter + BullMQ 队列 + delivery_status 迁移；列表排序与筛选重构；登录限速 | 后端 A/B |
| AI | 无新增（保 L1 稳定）；eva-config 返回真实层级健康（P0-8 后端部分） | AI 工程 |
| QA | 出站投递断网/重试/幂等；cron 后排序回归；全角色权限回归；中文输入法手测 | QA |
| 验收 | ① Telegram 真机完成"提问→EVA 答→追问→转人工→人工答→resolve"全程收到每条回复；② cron 运行后首屏无 closed；③ 84 项既有测试保持全绿 + 新增出站测试 | 产品 |
| 风险/依赖 | Telegram Bot API 需公网回调（准备内网穿透/测试机器人）；BullMQ 引入运维复杂度（Redis 已就位） | — |

**目标**：SLA/分配/宏/CSAT/成本中心齐备，具备 B2B 采购清单的硬项。

| 项 | 内容 | 负责人 |
|---|---|---|
| 功能 | P1-1 SLA 引擎；P1-2 分配与转交；P1-3 快捷回复+AI 起草；P1-5 打标上线；P1-7 CSAT；P1-8 成本中心看板；P1-11 Email 渠道 | 全员 |
| 前端 | SLA 倒计时列与视图；宏面板（/ 唤出）；AI 起草交互（来源引用展示）；成本看板 | 前端 A/B |

## 里程碑总览

```
D30  ── 闭环：客户收得到回复，收件箱可运营          （可开始内部试用）
D60  ── 好用：客户上下文/用户管理/KB 可读/AI 真摘要  （可给友好客户 beta）
D90  ── 可卖：SLA/分配/宏/CSAT/成本中心             （公开售卖，对标 Freshdesk）
D180 ── 领先：AI 干活/知识飞轮/驾驶舱/QA/试点按解决计费（差异化成立）
```

**贯穿全程的纪律**：① 状态机/锁/审计三条底线任何改动必须过既有 84 项测试；② 每个 AI 功能上线必须带"采纳率/解决率/成本"三个埋点，两个迭代内无正向数据即降级或下线；③ 所有新配置必须同时有 UI 与 API，杜绝新的"后端有前端无"。
